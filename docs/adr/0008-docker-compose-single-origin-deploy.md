# Ardoise deploys as two Docker images behind a single HTTPS origin

Ardoise had no deployment artifacts: it only ran through `vp dev` on a workstation, and production would have silently inherited the localhost dev defaults — a repo-relative SQLite file, better-auth trusted origins hardcoded to `http://localhost:1337`, and a Prisma CLI datasource pointing at a different file than the runtime. The operator deploys every app as a Portainer stack on his VPS, behind Nginx Proxy Manager, with images pulled from a container registry and data on Docker named volumes. We chose to fit that shape rather than invent an infrastructure of its own.

The delivery is two images, `fork-ardoise-api` (Bun + Prisma) and `fork-ardoise-web` (a small Bun/Hono server that serves the static build and proxies `/api/*` to the API), published to `ghcr.io/tituxmetal` by a GitHub Actions matrix job on every `main` push, and one paste-and-run compose file. A single hostname terminates TLS at NPM and reaches only the web container, which forwards `/api` (prefix stripped) to the API over the shared networks. The SQLite database lives on a named volume at `/data`, migrated on boot behind a house `RUN_MIGRATIONS` toggle, and covered by the operator's existing rsync volume backup.

The reasoning behind the load-bearing choices:

- **Two images, one origin, web served by Bun — not nginx.** The operator's other apps run Bun end-to-end (his Hono-only project and `car-cost-tracker` both serve through Bun); `apps/web` already depends on Hono. A ~30-line Bun server serves the History-API SPA with its deep-link fallback and proxies `/api` with the prefix stripped, mirroring the dev proxy contract. No second runtime.
- **Single origin via a server-side `/api` proxy, no CORS.** Browser traffic never leaves the one hostname, so there is no cross-origin session problem and no CORS config — the same-origin topology `car-cost-tracker` converged on after a long origin/cookie fight.
- **SQLite on a named volume.** The data is a single file on a Docker volume, so restart, redeploy and the house rsync backup all work at the volume level. A managed database was out of scope and would have broken the operator's backup story. This is the trade a future reader would otherwise question; revisiting it means a real data-migration, not a config change.
- **Secure cookies come from the `https` base URL, not the request scheme.** The web→API hop is plain HTTP. better-auth (verified against `^1.6.29`) decides the cookie `Secure` flag at init from config — never from the observed protocol or `X-Forwarded-Proto` — and has no `trustHost` (that is NextAuth vocabulary). Setting `BETTER_AUTH_URL` to the public `https` origin makes better-auth emit `Secure` cookies unconditionally, with no forwarded-header propagation through the proxy. `trustedOrigins` is env-driven; the public origin is auto-accepted.
- **Migrations run on boot, gated.** The API entrypoint runs `prisma migrate deploy` before serving while `RUN_MIGRATIONS` is set, failing fast so the restart policy retries. The operator removes the flag in Portainer once a release is stable — a house toggle, not an always-on rule.
- **Backup is the house rsync volume backup.** Ardoise ships no per-app backup tooling; the database volume is already in the operator's backup scope.

Consequences: deployment is manual by design — the CI only builds and publishes images, never deploys; updating is a Portainer stack redeploy that re-pulls the `prod` tag. Not in scope here: horizontal scaling, moving off SQLite to a managed database, and monitoring beyond the existing Portainer + restart policy.
